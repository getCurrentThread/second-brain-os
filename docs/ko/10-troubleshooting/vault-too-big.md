# 볼트가 너무 커졌을 때

<a id="symptoms"></a>

## 증상

답이 느려지고 흐릿해집니다. 에이전트가 스무 페이지를 읽고도 두루뭉술한 것을 내놓습니다. 그래프 뷰는 털뭉치가 됩니다. 어떤 주제를 다뤘는지 기억나지 않고, 확인하는 데 웹을 검색하는 것보다 오래 걸립니다.

<a id="what-it-usually-is-not"></a>

## 대개 원인이 아닌 것

디스크, 검색 속도, Obsidian이 아닙니다. 모두 문제없이 확장됩니다.

실제 원인은 검색의 경제성입니다. 인덱스가 읽는 데 실제 컨텍스트가 들 만큼 길어서, 에이전트는 그것을 건너뛰거나 페이지가 아니라 거기에 예산을 씁니다.

<a id="first-check-it-is-size-and-not-rot"></a>

## 먼저 규모 문제인지 부식인지 확인하기

[지표](../05-graphs/metrics.md)를 돌려 보십시오. 고아 페이지 비율이 20%인 볼트는 크기 문제가 아니라 링크 문제이며, 나눠도 도움이 되지 않습니다.

정말로 크면서 건강한 상태는 이렇게 보입니다. 낮은 고아 페이지 비율, 지배적인 연결 요소 하나, 범위 안의 평균 차수, 수백 항목이 넘는 인덱스.

<a id="summary-layers"></a>

## 요약 계층

첫 번째 해법이며 대개 충분합니다. 마스터 인덱스와 페이지 사이에 주제 영역별로 인덱스 하나를 두어, 에이전트가 비싼 읽기 한 번 대신 값싼 읽기 세 번을 하게 합니다. [확장](../09-maintenance/scaling.md)을 보십시오.

<a id="splitting"></a>

## 나누기

영역별로 나누고, 날짜로는 절대 나누지 마십시오. 서로에게 정말로 도움이 되지 않는 두 볼트일 때만 나눕니다.

영역을 넘나드는 연결이 더는 생기지 않는다는 점을 받아들이십시오. 그런 연결이 흔히 가장 흥미로우며, 그래서 나누기는 첫 대응이 아니라 늦은 수입니다.

<a id="archiving"></a>

## 아카이브

식은 자료는 `wiki/` 밖의 `archive/`로 옮깁니다. 검색은 여전히 되고, 인덱스와 그래프에서는 빠지며, 되돌릴 수 있습니다.

삭제보다 낫습니다. "식었다"는 추측이고 아카이브한 자료는 돌아올 수 있기 때문입니다.

<a id="rebuild-the-index"></a>

## 인덱스 다시 만들기

때로는 인덱스가 단순히 어긋났을 뿐입니다. 옮겨진 페이지의 항목, 중간에 실패한 실행이 추가한 페이지의 누락된 항목 같은 것입니다.

```
Rebuild index.md from the actual contents of wiki/. Group by type and theme, one
line of description per entry, and list gaps at the bottom.
```

값싸고, "볼트가 고장 난 것 같다"는 불만의 놀랄 만큼 많은 부분을 해결합니다.
