# 엉터리 글을 쓰는 에이전트

기술적으로는 맞는 주제를 다루는데 읽을 가치가 없는 페이지.

<a id="diagnose-the-source-first"></a>

## 먼저 원본부터 진단하기

지시문을 건드리기 전에 입력부터 확인하십시오. `raw/`의 파일을 열어 읽어 보십시오.

사람들이 에이전트 탓으로 돌리는 나쁜 페이지의 절반은 잘못된 추출에서 나옵니다. 단이 뒤섞인 PDF, 구두점 없는 자동 자막 트랜스크립트, 기사 대신 쿠키 배너를 수집한 클리핑 같은 것입니다.

에이전트는 뭉개진 텍스트로 좋은 페이지를 쓸 수 없고, 애를 먹고 있다고 알려 주지도 않습니다. [PDF](../03-ingestion/pdfs-and-books.md)와 [트랜스크립트](../03-ingestion/youtube-transcripts.md)를 보십시오.

<a id="then-check-claudemd"></a>

## 그다음 CLAUDE.md 점검하기

원본이 깨끗하다면 문제는 페이지 규약입니다.

모호한 페이지를 만드는 구체적인 원인은 이렇습니다. 페이지 유형마다 무엇이 들어가는지 정의가 없음, 어디에든 "요약하라"는 표현이 있음, 원본을 보지 않은 독자를 위해 쓰라는 지시가 없음, 링크를 걸라는 요구가 없음.

모양을 분명히 적어서 규약을 다시 쓰십시오. [페이지 유형](../04-structuring/page-types.md)을 보십시오.

<a id="add-an-example-not-another-rule"></a>

## 규칙을 더하지 말고 예시를 더하기

가장 효과가 크면서 가장 적게 쓰이는 수정입니다. 좋은 개념 페이지 하나를 `CLAUDE.md`에 통째로 넣어 목표로 삼게 하십시오.

규칙은 출력을 추상적으로 설명하고, 새 규칙은 저마다 다른 규칙과 상호작용합니다. 예시 하나는 목표를 곧바로 전달합니다. 사람에게 문체를 맞춰 달라고 부탁하면 그 사람이 달라고 할 것이 바로 예시입니다.

<a id="ask-what-it-was-working-from"></a>

## 무엇을 근거로 썼는지 묻기

```
You wrote [[page]]. Which parts of the source did you use, and what did you leave
out?
```

답은 대개 문제를 곧바로 짚어 줍니다. 일부 조각만 읽었거나, 원본이 주장한 것과 보고한 것을 구별하지 못했거나, 지시가 요약 쪽으로 끌어당긴 것입니다.

<a id="roll-back-and-re-run"></a>

## 되돌리고 다시 실행하기

규약을 고치고, 나쁜 페이지를 되돌리고, 다시 인제스트하십시오.

```bash
git checkout HEAD~1 -- wiki/
```

나쁜 페이지를 손으로 고치지 마십시오. 규약이 틀렸다면 그 실행에서 나온 모든 페이지에 같은 결함이 있으며, 눈에 띈 세 개만 손으로 고치면 나머지는 그대로 남습니다.
