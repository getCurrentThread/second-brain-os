# 컨텍스트 엔지니어링

프롬프트 엔지니어링은 "어떤 말을 쓸까?"를 물었습니다. 컨텍스트 엔지니어링은 "모델은 지금 이 순간 무엇을 보고 있고, 왜 그것을 보는가?"를 묻습니다. 에이전트에서는 두 번째 질문이 훨씬 중요합니다. 도구 결과, 읽은 파일, 지난 턴이 모두 한정된 윈도를 두고 경쟁하고, 그것을 선별하는 것이 하네스이기 때문입니다. Anthropic의 [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)가 이 분야의 기준이 되는 글입니다.

<a id="the-budget"></a>

## 예산

윈도를 보관함이 아니라 예산으로 다루십시오. 어텐션은 윈도가 차기 전에 떨어집니다. Chroma의 [컨텍스트 부패(context rot)](https://www.trychroma.com/research/context-rot) 연구는 윈도가 한계에 닿기 한참 전부터 입력이 늘수록 성능이 점점 떨어진다는 것을 보였습니다. 실전 규칙은 모델이 행동할 수 있는 선에서 신호 밀도가 높은 토큰을 가장 적게 담는 것입니다. 더하는 것은 모두 이미 있는 것을 희석합니다.

<a id="what-goes-in-and-when"></a>

## 무엇을 언제 넣는가

- **상시 포함**: 시스템 프롬프트, 도구 스키마, `CLAUDE.md` 같은 메모리 파일. 가볍고 안정적으로 유지하십시오. 안정된 프리픽스는 KV 캐시가 식지 않게 해 주는데, Manus는 이로 인한 [비용 차이가 10배](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)라고 측정했습니다.
- **필요할 때**: 파일 내용, 검색 결과, 스킬 본문, 문서. 필요할지도 모르는 것을 미리 싣지 말고, 에이전트에 검색 도구를 주어 필요한 것을 직접 가져오게 하십시오.
- **절대 넣지 않음**: 코드베이스 전체, API 응답 전체, 같은 지시의 열 가지 변형.

<a id="compaction"></a>

## 압축

긴 세션은 결국 어떤 윈도도 넘어섭니다. 압축은 트랜스크립트를 요약해(결정, 끝나지 않은 논의, 파일 경로) 그 요약으로 새로 시작하는 것입니다. 설계상 손실이 있습니다. 좋은 하네스는 도구 결과(부피가 크고 다시 필요한 일이 드뭅니다)를 중심으로 압축하고 의도를 보존합니다. [Claude Code](claude-code-as-harness.md)는 이를 자동으로 수행하며, 제어용으로 `PreCompact` 훅을 제공합니다.

<a id="memory-files"></a>

## 메모리 파일

압축과 세션을 넘어 살아남아야 하는 상태는 윈도 밖, 에이전트가 읽고 쓰는 일반 파일에 둡니다. 스크래치패드, `MEMORY.md`, 할 일 목록 같은 것입니다. 파일 시스템은 에이전트의 장기 메모리이고, 윈도는 작업 메모리입니다. 세컨드 브레인을 아는 독자라면 이 패턴을 알아보실 것입니다.

<a id="structured-outputs"></a>

## 구조화된 출력

다운스트림 코드가 에이전트의 답을 받아 쓴다면 스키마를 요구하십시오. 타입이 붙은 필드를 가진 JSON을 쓰고, 가능하면 API가 강제하게 합니다. 자유 서술은 사람을 위한 것이고, 구조는 파이프라인을 위한 것입니다. 모델이 얼버무리지 못하게 하는 효과도 있습니다. 필수 필드는 모델이 피할 수 없는 질문입니다.

<a id="failure-modes"></a>

## 실패 모드

- **컨텍스트 오염**: 환각으로 만들어진 "사실" 하나가 트랜스크립트에 들어와 세션의 나머지 동안 기정사실로 취급됩니다.
- **주의 분산**: 묻혀 있는 지시가 최근의 잡음에 밀립니다. 에이전트가 도구 출력 속에서 목표를 잊습니다.
- **충돌**: 시스템 프롬프트, 메모리 파일, 사용자가 내린 지시가 서로 모순되고, 임의로 해소됩니다.
- **비대화**: 아무도 읽지 않는 4만 토큰짜리 도구 결과가 이후 모든 턴마다 비용으로 나갑니다.

"모델이 멍청해졌다"는 보고 대부분은 이 넷 중 하나입니다. 실제 트랜스크립트를 읽어서 진단하십시오. 하네스는 그것을 볼 수 있게 해 주어야 합니다.

<a id="where-tools-fit"></a>

## 도구는 어디에 들어맞는가

대부분의 에이전트에서 도구 스키마와 결과는 컨텍스트를 가장 많이 먹는 단일 항목입니다. 그래서 도구 설계는 곧 컨텍스트 엔지니어링의 결정이며, 이것이 [도구와 MCP](tools-and-mcp.md)의 주제입니다.
