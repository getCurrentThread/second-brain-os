# 프로젝트 범위 지정

대부분의 사람이 건너뛰었다가, 볼트가 커질수록 산출물 품질이 왜 떨어지는지 의아해하게 되는 단계입니다.

에이전트가 볼트 전체를 향해 있으면 모든 작업이 지금까지 저장한 모든 것과 경쟁합니다. 내 삶 전체를 다루는 루트의 `CLAUDE.md`와, 그 밖에 관련 있다고 스스로 판단한 것을 읽습니다. 답은 더 넓어지고 더 얕아집니다.

프로젝트 하나를 향해 있으면 그 프로젝트의 `CLAUDE.md`를 읽고, 그 프로젝트의 파일을 보고, 눈앞의 일을 합니다.

<a id="how-to-scope"></a>

## 범위를 지정하는 방법

Obsidian에서 왼쪽 아래의 볼트 이름을 클릭한 다음:

**Manage vaults → Open folder as a vault → 프로젝트 폴더 선택 → Trust**

터미널에서는 같은 일이 이렇게 간단합니다:

```bash
cd ~/brain/projects/youtube-channel
claude
```

이제 에이전트는 그 프로젝트의 지시만 읽습니다.

<a id="when-to-use-which"></a>

## 무엇을 언제 쓰는가

**볼트 전체**는 여러 분야에 걸치는 모든 일에 씁니다. 계획, 검토, 어떤 주제에 대해 무엇을 아는지 묻기, 주간 유지보수, 인제스트가 그렇습니다. 지식 계층은 넓은 시야를 가지는 이유 그 자체입니다.

**프로젝트 하나**는 무엇이든 만들어 내는 일에 씁니다. 초안 작성, 구축, 이번 주 수치 분석이 그렇습니다. 좁은 컨텍스트, 하나의 목표, 표류 없음.

대략의 규칙은 이렇습니다. 볼트 전체는 계획하고, 프로젝트 하나는 내놓습니다.

<a id="passing-knowledge-into-a-project"></a>

## 프로젝트에 지식 넘기기

범위를 좁히면 에이전트가 위키와 단절되는데, 대개는 원하던 바이고 가끔은 아닙니다. 이를 잇는 방법은 두 가지입니다:

- 프로젝트의 `CLAUDE.md`에서 관련 개념 페이지를 링크하고, 정말 중요한 몇 개는 프로젝트의 `Inputs/`로 복사합니다.
- 아니면 먼저 볼트 전체에 조사 질문을 던지고, 답을 프로젝트의 `Inputs/`에 저장한 다음 범위를 좁혀 작업합니다.

두 번째가 낫습니다. 무엇이 중요한지 정하는 일을 사용자가 쥐고 있게 해 주며, 그 부분은 위임하지 말아야 합니다.
