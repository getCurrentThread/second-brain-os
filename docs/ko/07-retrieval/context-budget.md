# 컨텍스트 예산

에이전트가 페이지를 읽을 때마다 컨텍스트가 듭니다. 품질은 윈도가 다 차기 한참 전부터 떨어집니다. 더 많이 읽는다고 더 잘 읽는 것은 아닙니다.

<a id="progressive-disclosure"></a>

## 점진적 공개

효과가 있는 패턴은 이렇습니다.

1. **인덱스 먼저.** 무엇이 있는지 한 줄씩.
2. **중요한 페이지 열기.** 보통 세 개에서 여덟 개.
3. **링크는 한 번에 한 홉씩 따라가다가,** 새 페이지가 더 보태지 못하면 멈춥니다.

각 단계는 값싸고 다음 단계의 근거가 됩니다. 대안은 관련 있어 보이는 것을 처음부터 모두 싣는 것인데, 예산 대부분을 결국 무관한 것으로 드러나는 페이지에 쓰고, 쓸모 있는 페이지는 주의가 가장 약한 긴 컨텍스트의 가운데로 밀어 넣습니다.

<a id="why-not-paste-the-whole-vault"></a>

## 왜 볼트 전체를 붙여 넣지 않는가

긴 컨텍스트 모델은 많은 양을 담을 수 있어서, 검색을 아예 건너뛰고 싶어집니다.

그러지 말아야 할 이유가 둘 있습니다. 긴 컨텍스트에서 주의는 고르지 않아서, 가운데 있는 자료는 가장자리에 있는 자료보다 덜 안정적으로 쓰입니다. "Lost in the Middle"(중간 내용 소실)의 발견이 바로 이것이고, 위치가 애초에 중요한 이유입니다. 그리고 전부를 가지고 만든 답은 확인할 수 없습니다. 실제로 어느 페이지를 썼는지 알 길이 없기 때문입니다.

열어 볼 수 있는 다섯 페이지를 인용하는 답이, 열어 볼 수 없는 사백 페이지로 만든 유창한 답보다 낫습니다.

<a id="summary-layers"></a>

## 요약 계층

수백 페이지를 넘기면 마스터 인덱스와 페이지 사이에 인덱스를 한 단계 더 두십시오. 주제 영역마다 짧은 페이지를 하나씩 두고, 그 영역에 무엇이 있는지, 각 페이지가 무엇을 다루는지 적습니다.

에이전트는 마스터 인덱스를 읽고, 관련된 주제 인덱스 하나를 열고, 그다음 페이지를 엽니다. 비싼 읽기 한 번 대신 값싼 읽기 세 번입니다.

요약 계층이 쌓이게 두지 마십시오. 두 단계면 충분합니다. 세 단계가 되면 아무도 유지하지 않는 위계를 만드는 것이고, 요약의 요약은 그 아래에 있는 내용에서 어긋나기 마련입니다.

<a id="measuring-what-was-read"></a>

## 무엇을 읽었는지 확인하기

```
List the pages you read to answer that, in the order you opened them.
```

가끔 돌려 볼 만합니다. 두 가지 문제가 드러납니다. 여섯 페이지면 될 일에 서른 페이지를 읽는 에이전트, 그리고 볼트에 관련 페이지가 스무 개 있는데 세 개만으로 답하는 에이전트입니다. 둘 다 지시를 고쳐 해결할 수 있고, 어느 쪽도 답만 봐서는 보이지 않습니다.

<a id="subagents-for-wide-reads"></a>

## 넓게 읽을 때는 서브에이전트

질문이 정말로 많은 자료를 필요로 할 때는 [서브에이전트](../06-agents/subagents.md)를 보내십시오. 서브에이전트는 자기 컨텍스트에서 읽고 요약을 돌려주므로, 메인 세션은 출처가 아니라 답에 대해서만 비용을 냅니다.
