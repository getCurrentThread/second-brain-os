# 훅

훅은 스케줄이 아니라 이벤트에 반응해 실행됩니다. 매번 반드시 일어나야 하는 일에 알맞은 도구이며, 그런 일은 프롬프트 지시문이 결국 놓치고 마는 일과 정확히 겹칩니다.

<a id="worth-hooking"></a>

## 훅을 걸 만한 것

**쓰기 전 검증.** 프론트매터가 파싱되는지, 필수 필드가 있는지 확인합니다. 형식이 잘못된 페이지를 쓰는 시점에 잡으면 별일 아니지만, 한 달 뒤에 잡히면 그동안 모든 질의에서 보이지 않던 페이지입니다.

**실행 후 린트.** 깨진 링크가 생긴 순간에 드러납니다. 그때가 제대로 고칠 만큼 컨텍스트가 충분한 순간입니다.

**예약 실행 뒤 커밋.** 파일 마흔 개를 바꿨는데 커밋이 남지 않은 실행이 있을 가능성을 없애 줍니다.

**삭제 시 알림.** 어떤 삭제든, 언제든 드러납니다. 삭제는 드물어서 알림에 드는 비용이 없고, 울렸을 때는 의미가 큽니다.

<a id="not-worth-hooking"></a>

## 훅을 걸 가치가 없는 것

느린 것은 무엇이든. 파일을 쓸 때마다 돌면서 2초가 걸리는 훅은 마흔 페이지 인제스트를 90초의 멈춤으로 바꾸고, 결국 꺼 버리게 됩니다.

판단이 필요한 것은 무엇이든. 훅은 기계적인 점검입니다. 페이지가 충분히 좋은지 가르려는 훅은 양쪽 방향으로 다 틀립니다.

<a id="keep-them-fast-and-quiet"></a>

## 빠르고 조용하게 유지하기

훅은 1초보다 한참 짧게 끝나야 하고, 통과했을 때는 아무것도 출력하지 않아야 합니다. 성공했을 때도 로그를 남기는 훅은 훅의 출력을 무시하는 습관을 들이게 하며, 그런 습관은 훅 하나가 실패하는 날 훅이 아예 없는 것과 다름없습니다.

<a id="failure-behaviour"></a>

## 실패 시 동작

훅이 실패하면 작업을 막을지 명시적으로 정하십시오.

검증 훅은 막아야 합니다. 스키마 검증에 실패한 페이지는 쓰이면 안 됩니다. 알림 훅은 막지 말아야 합니다. 알림이 실패했다고 해서 작업을 잃을 이유는 없습니다.

나쁜 경우는, 막는 훅이 관련 없는 이유로 실패해서 예약된 인제스트를 일주일 동안 조용히 멈춰 세우는 것입니다. 무엇이든 막는 것은, 자신이 존재하는 이유 때문에만 실패할 만큼 단순해야 합니다.
