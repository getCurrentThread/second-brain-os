# 에이전트 평가

한 번의 완성(completion)은 함수이고, 에이전트는 프로세스입니다. 계획하고, 도구를 호출하고, 결과를 읽고, 자신의 실수에서 회복합니다(또는 회복하지 못합니다). 최종 답만 평가하는 것은 체스 한 판을 마지막 수만 보고 평가하는 것과 같습니다. 이 페이지는 [평가 설계](designing-evals.md)를 바탕으로 합니다.

<a id="trajectories-not-just-outcomes"></a>

## 결과만이 아니라 궤적

궤적 전체를 기록하십시오. 모델의 모든 턴, 도구 호출, 도구 결과, 재시도입니다. 그런 다음 두 수준에서 평가합니다.

- **결과**: 작업이 완료되었고 최종 상태가 올바른가? 에이전트가 끝냈다고 주장하는지가 아니라 *환경*을 기준으로(파일이 있는가, 행이 삽입되었는가, 테스트가 통과하는가) 확인하는 것이 가장 좋습니다. 에이전트는 능숙하게 승리를 선언합니다.
- **궤적**: 경로가 합리적이었는가? 단계 수를 세고, 루프를 감지하고, 조용히 무시된 도구 오류를 표시합니다. 성공률이 같은 두 에이전트라도, 한쪽이 40턴을 쓰고 토큰을 20배 태운다면 같지 않습니다.

<a id="tool-call-correctness"></a>

## 도구 호출의 정확성

가장 기계적이고 수확이 큰 검사는 다음과 같습니다.

- 의도에 맞는 도구 선택.
- 유효하고 컨텍스트에서 올바르게 추출된 인자(ID, 날짜, 필터. 에이전트가 조용히 실패하는 곳이 바로 여기입니다).
- 지켜진 순서 제약(`answer` 전에 `search`, `write` 전에 `read`).
- 오류 처리: 궤적 중간에 도구 실패를 주입하고, 에이전트가 결과를 지어내지 않고 재시도하거나 보고하는지 확인합니다.

이것들은 트레이스에 대한 코드 단언이지 판정자 호출이 아닙니다. [LLM 판정자(LLM-as-judge)](llm-as-judge.md)는 "계획이 합리적이었는가" 같은 질문에 아껴 두십시오.

<a id="environment-based-evals"></a>

## 환경 기반 평가

가장 확실한 방식은 이렇습니다. 에이전트에게 샌드박스 환경(Docker 컨테이너, 시드 데이터가 들어간 데이터베이스, 모의 API)을 주고, 끝난 뒤의 *상태*를 실행 가능한 검사로 채점합니다. 준비는 결정적이고, 정리는 프로그램이 하며, 채점에 모호함이 없습니다. 트랜스크립트 골든 세트보다 만들기는 품이 더 들지만, 상태를 바꾸는 작업이라면 무엇이든 그럴 가치가 있습니다.

<a id="harness-benchmarks-2026-edition"></a>

## 하네스 벤치마크, 2026년판

공개 벤치마크는 모델과 하네스를 비교하기 위한 것이지 자기 제품을 측정하기 위한 것이 아닙니다. 그래도 좋은 환경 기반 평가(eval)가 어떤 모습인지는 보여 줍니다.

- [SWE-bench](https://www.swebench.com/) 계열: 실제 GitHub 이슈를 저장소의 테스트로 채점합니다. 사람이 검수한 500개인 SWE-bench Verified가 여전히 코딩 에이전트의 대표 수치이며, 프런티어 모델은 이제 80~90점대에 있고, 원래 벤치마크가 포화되면서 계열에는 더 어려운 변형이 계속 생겨나고 있습니다.
- [Terminal-Bench](https://www.tbench.ai/): 2.0은 실제 Docker 컨테이너 안에서 사람이 검수한 터미널 작업 89개를 실행 가능한 테스트로 채점합니다. 가져다 쓰기에 가장 깔끔한 템플릿입니다.
- [GAIA](https://arxiv.org/abs/2311.12983): 웹, 도구, 다단계 추론이 필요한 범용 어시스턴트 작업.
- [tau2-bench](https://github.com/sierra-research/tau2-bench): 도구-에이전트-*사용자* 상호작용을 시뮬레이션된 고객과 진행합니다. 정책 제약 아래의 대화를 측정합니다.
- [Inspect Evals](https://github.com/UKGovernmentBEIS/inspect_evals): 위 벤치마크의 구현 200개 이상을 하나의 프레임워크로 묶었습니다.

<a id="ci-integration"></a>

## CI 통합

평가는 노트북이 아니라 파이프라인에 속합니다.

- 모든 PR에는 작은 스모크 스위트(결정적 검사만)를, 전체 스위트는 매일 밤과 릴리스 전에 실행합니다.
- 임계값으로 병합에 게이트를 겁니다. 케이스마다 N번 시도를 실행하고 평균을 기준으로 삼습니다.
- CI에서 모델 버전을 고정하고, 모델 버전 상향도 다른 변경과 똑같이 스위트를 통과해야 하는 변경으로 취급합니다.

이 과정을 덜 고통스럽게 만들어 주는 도구는 [평가 도구](tooling.md)에서 살펴봅니다.
