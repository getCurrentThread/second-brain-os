# LLM 판정자

일부 검사는 코드로 합니다. 정확 일치, 정규식, JSON 스키마, "SQL이 실행되는가" 같은 것입니다. 나머지, 곧 어조, 충실성, 답이 정말 질문에 답하고 있는지는 읽을 줄 아는 채점기가 필요합니다. 그 채점기는 대개 또 다른 LLM입니다. 쓸모 있고 저렴하지만, 보정하기 전에는 믿을 수 없습니다.

<a id="writing-the-judge-prompt"></a>

## 판정자 프롬프트 쓰기

판정자 프롬프트는 희망 사항이 아니라 직무 기술서입니다.

- 판정자 하나에 질문 하나. "주어진 컨텍스트가 이 주장을 뒷받침하는가: 예/아니오"가 "전반적인 품질을 평가하라"보다 낫습니다.
- 이진 출력, 그리고 *판정보다 먼저 쓰는 서면 근거*를 필수로 요구합니다. 근거는 디버깅의 단서입니다. 판정부터 내리는 판정자는 합리화를 합니다.
- 통과와 실패의 완성된 예시를 2~4개 넣습니다. 특히 경계에 걸친 사례가 중요합니다.
- 제품이 받았던 것과 같은 컨텍스트를 줍니다. 검색된 문서 없이 RAG 답변을 채점하는 판정자는 추측하는 것입니다.

프롬프트 속 루브릭은 구체적으로 유지하십시오. "도움이 되는"이나 "고품질" 같은 형용사가 아니라, 오류 분석에서 나온 실패 분류([평가 설계](designing-evals.md) 참고)를 그대로 옮깁니다.

<a id="calibration-against-human-labels"></a>

## 사람 레이블로 보정하기

보정하지 않은 판정자는 자신감 넘치는 난수 생성기입니다. 절차는 Hamel Husain의 [판정자 가이드](https://hamel.dev/blog/posts/llm-judge/)에서 그대로 가져왔습니다.

1. 도메인 전문가가 출력 50~100개에 통과/실패 레이블과 짧은 이유를 붙입니다.
2. 같은 세트에 판정자를 돌려 일치도를 측정합니다. 단순 정확도가 아니라 클래스별 일치도를 보고합니다. 대부분 좋은 결과로 이루어진 데이터에서는 항상 "통과"라고 답하는 판정자도 90%를 받기 때문입니다.
3. 불일치를 하나도 빠짐없이 읽습니다. 루브릭을 고치거나, 자신의 레이블이 일관되지 않았음을 발견합니다. 둘 다 실제로 일어납니다.
4. 일치도가 따분할 만큼 안정될 때까지 반복하고, 그 뒤로는 분기마다, 그리고 판정자 모델을 바꿀 때마다 다시 확인합니다.

Shreya Shankar의 [Who Validates the Validators?](https://arxiv.org/abs/2404.12272)는 이 루프를 연구로 다룬 글입니다.

<a id="known-bias-failure-modes"></a>

## 알려진 편향 실패 모드

[MT-Bench 논문](https://arxiv.org/abs/2306.05685) 이후 계속 문서화되어 왔고, 2026년에도 여전합니다.

- **위치 편향.** 페어와이즈 비교에서 판정자는 첫 번째(때로는 두 번째) 답을 선호합니다. 순서를 바꿔 평균을 내십시오. 그렇지 않으면 비교는 의미가 없습니다.
- **장황함 편향.** 정확성이 같아도 더 긴 답이 더 높은 점수를 받습니다. 길이를 제한하거나 길이로 점수를 주지 말라고 명시적으로 지시한 뒤, 효과를 검증하십시오.
- **자기 선호.** 모델은 자기 계열이 낸 출력에 더 높은 점수를 줍니다. 가능하면 채점 대상과 다른 모델로 판정하십시오.
- **밝힌 의도에 대한 아첨.** 사용자가 내세운 목표를 넣으면 판정자는 결과가 아니라 노력을 채점합니다.

<a id="when-judges-lie"></a>

## 판정자가 거짓말할 때

판정자는 다음 경우에 조용히 실패합니다. 수학과 산술, 틈새 도메인 사실, 미묘한 지시 위반, 그리고 판정 모델 자신도 틀릴 만한 모든 것입니다. 검사를 코드로 *할 수 있다면* 코드로 만드십시오. 판정자는 정말로 언어적인 판단에만 쓰고, 판정 표본을 사람이 계속 점검하게 하고, 단계별 검사와 모순되는 릴리스를 판정자 점수가 통과시키도록 두지 마십시오. 둘을 결합하는 방법은 [에이전트 평가](agent-evals.md)를 참고하십시오.
