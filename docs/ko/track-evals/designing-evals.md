# 평가 설계

평가(eval)는 테스트 케이스만큼만 좋습니다. "우리 봇이 가끔 틀린다"에서 믿을 수 있는 스위트까지 가는 길은 실패 모드를 거칩니다. 무엇이 잘못되는지 이름을 붙이고, 그것을 일으키는 케이스를 만드는 것입니다. 이 페이지는 [평가가 필요한 이유](why-evals.md)에서 설명한 오류 분석을 이미 마쳤다고 가정합니다.

<a id="golden-sets"></a>

## 골든 세트

골든 세트는 제품을 이해하는 사람이 엄선한, 정답 기대치가 붙은 고정 입력 모음입니다. 경험칙은 다음과 같습니다.

- 프로덕션 트레이스에서 먼저 가져오고, 지어내는 것은 그다음입니다. 실제 입력은 직접 쓸 수 있는 어떤 것보다 기이합니다.
- 이름 붙은 실패 모드마다, 과거에 그 실패를 일으킨 케이스를 최소한 몇 개는 넣습니다.
- 평범한 성공 사례도 넣습니다. 그렇지 않으면 실패 사례에만 과적합해 정상 경로가 회귀합니다.
- 코드 옆에 git으로 버전 관리합니다. 아무도 diff를 볼 수 없는 골든 세트는 아무도 믿지 않는 골든 세트입니다.

<a id="synthetic-data"></a>

## 합성 데이터

트래픽이 적을 때, 즉 출시 전이거나 드물지만 중요한 경로일 때는 케이스를 생성합니다. LLM으로 의도적으로 고른 차원, 곧 페르소나, 표현, 길이, 언어, 적대적 의도를 바꿔 가며 만듭니다. 주의할 점이 두 가지 있습니다.

- 합성 입력은 괜찮지만 합성 *레이블*은 순환 논리입니다. 모델이 직접 지어낸 데이터로 다른 모델을 채점해 봐야 증명되는 것이 거의 없습니다. 사람이 레이블을 표본 점검하게 하십시오.
- "다양한 예시 100개 만들어 줘"가 아니라 차원의 스키마를 따라 생성하십시오. 전자는 같은 아이디어 세 개를 변주한 예시 100개를 낳습니다.

<a id="graded-vs-binary"></a>

## 등급 점수와 이진 판정

이진 판정을 선호하십시오. 통과/실패는 기준을 정의하도록 강제하고, 사람 사이의 의견 차이도 곧바로 드러납니다. 1~5점 "품질" 척도는 대개 채점기의 기분을 측정합니다. 두 어노테이터가 같은 출력에 태연히 3점과 4점을 매기고, 얻는 것은 없습니다. 어떤 것에 정말로 정도가 있다면, 모호한 스칼라 하나가 아니라 여러 개의 이진 검사(출처를 인용했는가: 예/아니오, 올바른 출처인가: 예/아니오)로 쪼개십시오. 채점기가 [LLM 판정자(LLM-as-judge)](llm-as-judge.md)일 때는 이것이 두 배로 중요합니다.

<a id="per-step-vs-end-to-end"></a>

## 단계별과 엔드투엔드

단일 호출에서는 이 문제가 생기지 않습니다. 에이전트에는 둘 다 필요합니다.

- **엔드투엔드**: 작업이 끝났는가? 사용자에게 중요한 숫자입니다.
- **단계별**: 도구 호출마다 타당했는가, 검색이 올바른 문서를 가져왔는가, 계획이 요청을 다뤘는가? 엔드투엔드가 실패했을 때 실패 지점을 좁혀 줍니다.

엔드투엔드는 깨졌다는 *사실*을, 단계별은 *어디서* 깨졌는지를 알려 줍니다. 자세한 내용은 [에이전트 평가](agent-evals.md)에 있습니다.

<a id="sample-sizes-that-matter"></a>

## 의미 있는 표본 크기

작은 스위트는 거짓말을 합니다. 케이스가 20개라면 70%에서 80%로의 변화는 예시 두 개의 차이, 곧 노이즈입니다. 대략의 지침은 다음과 같습니다.

- 20~50개: 플라이휠을 돌리기 시작하기에는 충분하지만, 프롬프트를 비교하기에는 부족합니다.
- 신경 쓰는 실패 모드마다 100~200개: 약 10포인트의 차이가 의미를 갖기 시작합니다.
- 확률적 시스템은 케이스마다 여러 번 실행하고, 운 좋은 한 번이 아니라 분포를 보고합니다.

확신이 서지 않으면 자축하기 전에 신뢰 구간을 계산하십시오. 구간이 "개선"과 "회귀"를 모두 포함한다면, 출시하지 말고 케이스를 더 모으십시오.
