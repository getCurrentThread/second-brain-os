# 프론트매터 스키마

프론트매터는 볼트를 텍스트 검색이 아닌 다른 방식으로 질의할 수 있게 해 줍니다. 쓰는 데 비용이 들지 않고, Dataview와 스크립트, 그리고 에이전트 자신이 형태로 항목을 찾을 때 쓰는 것이 바로 이것입니다.

<a id="the-schema"></a>

## 스키마

```yaml
---
title: Canonical name
type: source | entity | concept | synthesis
created: YYYY-MM-DD
updated: YYYY-MM-DD
aliases: [other names this is known by]
tags: [two or three]
---
```

자료 페이지는 다음을 더합니다.

```yaml
url: https://...
author:
published: YYYY-MM-DD
```

엔티티 페이지는 `kind: person | org | product | tool`을 더합니다.

<a id="why-each-field-earns-its-place"></a>

## 각 필드가 필요한 이유

`type`은 모든 구조 질의와 모든 린트 검사를 움직입니다. 이것이 없으면 개념이 몇 개인지 묻거나, 개념이 하나도 붙지 않은 자료를 찾을 수 없습니다.

`updated`는 점검을 가능하게 합니다. 오래된 개념 페이지는 볼트가 썩는 주된 경로인데, 날짜가 없으면 그런 페이지를 찾을 수 없습니다.

`aliases`는 같은 대상에 이름이 셋일 때 위키링크가 제대로 연결되게 합니다. [이름 짓기와 별칭](naming-and-aliases.md)을 참고하십시오.

자료 페이지의 `url`은 인용과 단순한 주장을 가르는 것입니다. 이것이 없는 자료 페이지는 검증할 수 없습니다.

<a id="tags"></a>

## 태그

페이지당 두세 개, 실제로 관리하는 작은 통제 어휘에서 고릅니다.

태그는 한 가지 특정한 방식으로 실패합니다. 어휘가 의미를 잃을 때까지 커지는 것입니다. 한 번씩만 쓰인 태그 50개는 태그가 없는 것보다 나쁩니다. 분류 체계가 있는 듯한 인상만 주고 분류의 일은 하나도 하지 않기 때문입니다.

태그 목록은 `CLAUDE.md`에 두고, 에이전트가 기존 태그를 쓰거나 새 태그를 조용히 만들어 내지 말고 명시적으로 제안하게 지시합니다.

구조의 부담은 폴더와 링크가 집니다. 태그는 그 어느 쪽에도 맞지 않는, 여러 범주에 걸치는 성질을 위한 것입니다. `unverified`, `to-revisit`, `disputed` 같은 것들입니다.

<a id="empty-fields"></a>

## 빈 필드

추측으로 채우지 말고 필드를 빼 둡니다. `published`가 없다는 것은 알 수 없다는 뜻이며, 에이전트는 이를 솔직하게 말할 수 있습니다. 추측한 날짜는 3주 뒤 개념 페이지에서 사실이 됩니다.

<a id="keep-it-stable"></a>

## 안정적으로 유지하기

스키마에 필드를 하나 더하면 모든 페이지를 백필하거나, 질의가 오래된 절반을 놓치는 뒤섞인 볼트를 감수하게 됩니다.

스키마는 일찍 정하고, 작게 유지하고, 드물게 바꿉니다. 바꿀 때는 변경이 새 페이지에만 적용되게 두지 말고, 볼트 전체에 백필을 한 번에 돌립니다.
