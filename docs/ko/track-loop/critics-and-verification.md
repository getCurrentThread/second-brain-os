# 크리틱과 검증

루프는 판정자만큼만 좋습니다. 이제 생성은 값쌉니다. 모델은 몇 푼이면 또 한 번의 시도를 만들어 냅니다. 그래서 병목이 코드를 쓰는 일에서 그 코드가 동작함을 증명하는 일로 옮겨 갔습니다. 크리틱 역할을 하는 것이 무엇이든, 그것이 루프가 진전을 쌓을지 쓰레기를 쌓을지 결정합니다.

<a id="done-versus-claims-done"></a>

## 완료와 완료 주장

모델은 트랜스크립트가 끝난 것처럼 보이게 하도록 훈련됩니다. "모든 테스트가 통과했고 기능이 완성되었습니다"는 산문이고, 산문은 증거가 아닙니다. 에이전트가 테스트를 돌리지 않았을 수도, 엉뚱한 테스트를 돌렸을 수도, 실패하는 테스트를 슬쩍 지웠을 수도 있습니다. 여기서 나오는 규칙은 절대적입니다. 루프는 확인하지, 묻지 않습니다. 완료는 세상의 속성입니다. 종료 코드, diff, 초록불이 켜진 파이프라인처럼, 일을 한 프로세스가 아닌 다른 무엇이 측정해야 합니다. [종료 조건](stop-conditions.md)이 에이전트 자신의 보고를 배제하는 것도 같은 이유입니다.

<a id="code-as-critic"></a>

## 크리틱으로서의 코드

결정론적 크리틱을 먼저 쓰십시오. 테스트 스위트, 타입 체커, 린터, 빌드입니다. 실행당 비용이 들지 않고, 매번 똑같은 판정을 내리며, 설득되지 않습니다. 약점은 코드에 담긴 것만 판단한다는 점이고, 압박받는 에이전트는 문구만 충족시킵니다. 고전적인 수법이 실패하는 테스트를 약하게 만들거나 지우는 것입니다. 그러니 크리틱을 만드는 쪽의 손이 닿지 않는 곳에 두십시오. 에이전트의 `tests/` 쓰기 권한을 막거나, 검증 단계 직전마다 테스트 디렉터리를 git에서 복원하십시오. 만드는 쪽이 고칠 수 있는 체커는 체커가 아닙니다.

<a id="llm-critics-with-narrow-rubrics"></a>

## 좁은 기준을 가진 LLM 크리틱

코드가 내릴 수 없는 판단도 있습니다. diff가 최소한인가, 오류 처리가 진짜인가 장식인가, 변경이 작업 범위 안에 머물렀는가 하는 것들입니다. 이럴 때는 두 번째 모델 호출을 크리틱으로 쓰되, 가차 없이 좁히십시오. 좋은 크리틱 프롬프트는 검사 가능한 규칙을 세 개에서 다섯 개 명시하고, 구조화된 판정(PASS, 또는 위치와 수정안을 붙인 위반 목록)을 요구하며, 그 밖의 것에 대한 논평을 명시적으로 금지합니다. 기준이 넓은 "이 코드를 리뷰하라" 크리틱은 그럴듯한 소음을 만들고, 다음 시도는 결함 대신 스타일 의견을 쫓느라 예산을 태웁니다.

LLM 크리틱은 [평가 핸드북의 LLM 판정자(LLM-as-judge)](../track-evals/llm-as-judge.md)에 기록된 모든 실패 양상을 물려받습니다. 관대함 편향, 장황한 답 선호, 자기 선호입니다. 여기서는 마지막이 가장 중요합니다. 같은 컨텍스트에서 모델이 자기 작업을 채점하게 두지 마십시오. 크리틱은 새 컨텍스트를 받아 diff와 기준만 보고, 가능하면 다른 모델이어야 합니다. [실습: 크리틱](build-critic.md)이 바로 이 구조를 시도 사이에 연결합니다.

<a id="verifier-asymmetry"></a>

## 검증기 비대칭

루프가 애초에 통하는 이유는 확인이 대개 하는 것보다 싸기 때문입니다. 에이전트가 스무 분 걸려 쓴 것을 테스트 스위트는 몇 초 만에 검증합니다. 이 비대칭이 엔진입니다. 값싼 시도를 많이 사고 판단에만 제값을 치를 수 있게 해 주기 때문입니다. 어떤 작업을 루프로 돌릴지도 이것이 알려 줍니다. 값싸고 믿을 만한 검증기가 있는 작업(실패하는 테스트, 재현되는 버그, 벤치마크 수치)은 루프가 아주 잘 돕니다. 검증이 작업만큼 비싼 작업(아키텍처 취향, 글의 품질, 제품 판단)은 그렇지 않으며, 그렇다고 우기면 자신만만한 쓰레기를 대규모로 만들어 냅니다. 루프를 만들기 전에 검증기의 값을 매겨 보십시오. 진짜 검증기를 마련할 수 없다면 사람을 자리에 그대로 두십시오.
