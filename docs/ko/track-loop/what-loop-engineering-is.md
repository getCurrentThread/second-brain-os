# 루프 엔지니어링이란

루프 엔지니어링은 에이전트를 돌리는 제어 시스템을 설계하는 분야입니다. 무엇을 프롬프트할지, 결과를 어떻게 검증할지, 재시도할지, 언제 멈출지를 정하는 장치입니다. 이 일들을 턴마다 손으로 하던 방식에서 벗어나, 한 번 코드로 옮겨 둡니다. 프롬프트 엔지니어링은 메시지 한 통을 최적화했습니다. 루프 엔지니어링은 사이클을 최적화합니다. 다음에 누가 모델을 호출하는지, 어떤 목표를 향해, 어떤 테스트로 판정하고, 어떤 예산 안에서 도는지입니다.

<a id="where-the-term-came-from"></a>

## 용어의 유래

2026년 6월 7일 Peter Steinberger가 이 변화에 이름을 붙인 글을 올렸습니다. "You shouldn't be prompting coding agents anymore. You should be designing loops that prompt your agents."(이제 코딩 에이전트에 프롬프트를 쓰지 마십시오. 에이전트에 프롬프트를 던지는 루프를 설계하십시오.) 이 글은 하루 만에 수백만 번 조회되었습니다. 곧이어 Addy Osmani의 에세이 "Loop Engineering"이 나왔고(O'Reilly Radar가 6월 22일에 전재했습니다), 이 개념에 해부도를 그려 주었습니다. 자동화, 워크트리, 스킬, 커넥터, 서브에이전트, 그리고 실행 사이에도 진행 상황이 남도록 하는 외부 상태입니다. Anthropic의 Boris Cherny는 이렇게 단언했습니다. "I don't prompt Claude anymore. I have loops running that prompt Claude... My job is to write loops."(나는 더 이상 Claude에 프롬프트를 쓰지 않습니다. Claude에 프롬프트를 던지는 루프를 돌립니다. 내 일은 루프를 쓰는 것입니다.)

실무 관행은 이름보다 오래되었습니다. Geoffrey Huntley의 Ralph 루프는 2025년 7월로 거슬러 올라가고, Simon Willison은 그해 9월에 "Designing agentic loops"를 써서 에이전트를 "runs tools in a loop to achieve a goal"(목표를 이루기 위해 루프 안에서 도구를 실행하는 것)이라고 정의했습니다. 2026년 6월은 이 분야가 이름을 얻은 때일 뿐입니다. 이 핸드북을 쓰는 시점에서 석 달밖에 되지 않았으니, 용어는 계속 바뀔 수 있습니다.

<a id="prompt-engineering-versus-loop-engineering"></a>

## 프롬프트 엔지니어링과 루프 엔지니어링

손으로 프롬프트를 쓰면 판단력을 한 턴씩 씁니다. 출력을 읽고, 좋은지 판단하고, 다음에 던질 말을 고릅니다. 루프 엔지니어링은 그 판단력을 맨 앞에서 한 번만 씁니다. 대상은 네 가지 결과물입니다. 실행 가능한 테스트로 표현한 목표, 실패를 되먹이는 재시도 정책, 예산, 종료 규칙입니다. 그 뒤에는 루프가 에이전트에 프롬프트를 던지고, 사람은 결과를 검토합니다. 병목이 지시문을 쓰는 일에서 결과를 증명하는 일로 옮겨 갑니다.

<a id="the-four-pillars"></a>

## 네 기둥

- **컨텍스트 위생**: 턴과 시도 사이에 무엇을 남기고 무엇을 일부러 버릴지 정합니다. [컨텍스트 위생](context-hygiene.md)에서 다룹니다.
- **종료 조건**: 목표 테스트, 예산, 래칫, 공회전 감지. "에이전트가 끝났다고 말했다"는 조건이 아니라 주장이기 때문입니다. [종료 조건](stop-conditions.md)에서 다룹니다.
- **진짜 크리틱**: 에이전트가 반박할 수 없는 검증이며, 일을 한 에이전트와 분리되어 있습니다. [크리틱과 검증](critics-and-verification.md)에서 다룹니다.
- **멱등 도구**: 루프가 재시도하는 것은 언젠가 두 번 실행됩니다. 따라서 에이전트가 닿을 수 있는 모든 쓰기는 반복해도 안전해야 합니다. 재시도된 "청구서 생성"이 청구서를 두 장 만들어서는 안 됩니다. 두 번째 호출이 아무 일도 하지 않도록 도구를 설계하십시오.

<a id="not-the-same-thing-as-a-harness"></a>

## 하네스와는 다른 것

이 사이트에는 이미 [에이전트 하네스](../track-harness/what-a-harness-is.md) 핸드북이 있습니다. 모델을 둘러싼 장치, 즉 안쪽의 while 루프, 도구 스키마, 권한, 컨텍스트 윈도 관리를 다룹니다. 루프 엔지니어링은 그 장치 위에 얹는 제어 규율입니다. 하네스는 한 턴을 실행합니다. 루프는 다음 턴이 있어야 하는지, 무엇을 시도할지, 누가 판정할지, 전체 작업이 언제 끝날지를 정합니다. 둘 다 필요합니다. 루프 규율 없는 좋은 하네스는 검증되지 않은 결과물을 아주 빠르게 쏟아 내는 방법이고, 쓸 만한 하네스 없이 루프 규율만 있으면 믿고 조종할 대상이 없습니다.
