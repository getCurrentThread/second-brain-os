# 컨텍스트 위생

하네스 핸드북은 [컨텍스트 엔지니어링](../track-harness/context-engineering.md)을 다룹니다. 한 세션 안에서 모델이 보는 내용을 턴마다 골라 다듬는 일입니다. 컨텍스트 위생은 같은 규율을 루프 차원에서 적용한 것입니다. 턴과 턴 사이, 시도와 시도 사이에 무엇이 살아남는지, 그리고 그만큼 중요한 문제로 무엇을 일부러 없애는지를 다룹니다. 하네스는 윈도를 관리하고, 루프는 수명 주기를 관리합니다.

<a id="editing-within-long-runs"></a>

## 긴 실행 중의 편집

오래 도는 루프는 무엇보다 먼저 컨텍스트 고갈로 죽습니다. Anthropic의 컨텍스트 관리 작업은 이 문제를 정면으로 다룹니다. 컨텍스트 편집은 윈도가 한계에 가까워지면 오래된 도구 호출과 결과를 자동으로 비우면서 대화의 흐름은 그대로 둡니다. 100턴짜리 웹 검색 평가에서 컨텍스트 편집 덕분에 에이전트는 그냥 두면 실패했을 워크플로를 끝까지 마쳤고, 토큰 소비는 84% 줄었습니다. 다단계 벤치마크에서는 편집만으로 기준선보다 성능이 29% 올랐고, 메모리 도구와 함께 쓰면 39% 올랐습니다. 교훈은 한 벤더를 넘어 일반화됩니다. 오래된 도구 출력은 윈도에서 가치가 가장 낮고 양은 가장 많은 것이며, 이를 한 번도 솎아 내지 않는 루프는 쓰레기에 월세를 내는 셈입니다.

<a id="files-as-the-loops-memory"></a>

## 루프의 메모리 역할을 하는 파일

살아남아야 하는 상태는 윈도 밖, 에이전트가 읽고 쓰는 평범한 파일에 둡니다. `plan.md`, 체크박스가 있는 `TODO.md`, 지금까지의 최고 점수를 기록한 래칫 파일 같은 것입니다. 모델은 실행 사이에 잊어버리지만 저장소는 기억합니다. 이것이 Osmani가 말한 "외부 상태" 구성 요소이고, 모든 무인 패턴 뒤에 있는 조용한 비결입니다. [야간 루프](build-overnight.md)는 사실 래칫 파일과 보고서 파일에 while 루프를 두른 것일 뿐입니다. 세컨드 브레인을 아는 독자라면 이 방식이 낯익을 것입니다. 작업 기억은 휘발되므로, 중요한 것은 무엇이든 적어 둡니다.

## 시도마다 새 컨텍스트

직관에 반하는 규율이며, Ralph 루프를 돌리던 사람들이 어렵게 배웠습니다. 시도와 시도 사이에는 트랜스크립트를 버리십시오. 실패한 시도의 트랜스크립트는 대부분 혼란의 기록입니다. 틀린 가설, 막다른 검색, 사과 같은 것들입니다. 이것을 다음 시도에 가져가면 그 혼란을 확립된 사실로 받아들여 시도를 오염시킵니다. Geoffrey Huntley의 원조 루프는 반복마다 에이전트를 일부러 맨 처음 상태로 재시작합니다. 같은 파일이 매 패스마다 컨텍스트에 들어가므로, 프롬프트 파일과 저장소가 유일한 기억이 되고, 각 시도는 깨끗한 윈도와 목표를 받습니다.

시도 사이의 틈을 건너가는 것은 이력이 아니라 정제한 요약입니다. 실패한 테스트 출력, 크리틱이 나열한 결함 목록, 현재 할 일 상태입니다. [목표 테스트 실습](build-goal-test.md)이 되먹이는 것이 정확히 이것입니다. 목표 스크립트의 stderr이고, 그 밖에는 아무것도 없습니다.

<a id="what-to-carry-what-to-burn"></a>

## 가져갈 것, 버릴 것

- **가져갈 것**: 목표, 할 일 파일, 마지막 검증기 출력, 크리틱의 판정, 래칫 점수.
- **버릴 것**: 탐색 트랜스크립트, 대량의 도구 출력, 에이전트가 늘어놓은 중계 멘트, 일이 얼마나 잘 되어 가는지에 대해 에이전트가 한 말 전부.

각 항목을 가져갈지 버릴지 가르는 기준은 직설적입니다. 새로 투입된 유능한 에이전트가 이것을 눈앞에 두면 더 잘 일하겠는가? 검증기 출력은 이 기준을 통과합니다. 지난 시도가 실패한 토큰 4만 개짜리 로그는 통과하지 못합니다. 위생이란 다음 시도를 대신해 결정하는 일이고, 그래서 모델이 아니라 루프의 몫입니다.
